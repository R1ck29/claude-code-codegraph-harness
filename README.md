# Claude Code Codegraph Harness

Evaluation-first tooling for comparing code-graph backends in Claude Code and assembling an offline, cross-platform extension bundle.

> Status: `v0.1.0-eval`. This repository does not select a backend and does not claim a 10x token reduction.

## Why this repository exists

Teams often distribute a Claude Code harness as a mix of plugins and Rules installed by scripts. Some users cannot access GitHub from their workstations and instead receive an approved ZIP from an internal software portal. This repository provides a public, vendor-neutral source for that workflow:

1. compare the current Claude Code workflow, Graphify, Codebase-Memory, and hybrid routing under the same conditions;
2. decide whether upstream can be used unchanged, needs a thin wrapper, requires a maintained fork, or should not be adopted;
3. assemble a checksummed ZIP that an internal pipeline can enrich with approved binaries and private Rules;
4. install the plugin and public Rules on macOS or Windows without downloading dependencies at install time.

The originating article and its referenced evidence are separated in [Research context](docs/research-context.md). In particular, the article's one-tenth token headline is not a measured Graphify result and is not treated as expected ROI here.

The public repository never contains internal repositories, prompts, results, URLs, managed settings, signing keys, private Rules, generated graphs, or unreviewed vendor binaries.

## No-code-egress boundary

This repository does not upload source and the comparison runner itself makes no network request. It does launch the configured `claude` command and optional backend subprocesses; their network behavior is outside the Python runner's authority. Do not run it on company source until the organization has verified the approved Claude Code data path and has enforced process-level egress denial for every graph backend, including DNS, update checks, telemetry, error reporting, and child processes. Local `stdio` MCP alone is not a network control.

## Quick start for evaluators

Requirements:

- Python 3.10 or later;
- Claude Code installed and authenticated;
- vendor executables prepared separately for non-baseline conditions.

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e .
codegraph-harness doctor
codegraph-harness evaluate \
  --tasks evaluation/tasks/smoke.json \
  --conditions evaluation/configs/conditions.example.json \
  --repo /path/to/a-public-fixture \
  --harness-root . \
  --output-dir /secure/local/results/run-001 \
  --data-classification public-fixture \
  --condition baseline
```

The runner never downloads Graphify or Codebase-Memory. Candidate profiles point to binaries or environments supplied by the evaluator. Raw stdout/stderr are hashed but not stored by default. If an approved evaluation requires raw output, pass `--store-raw-artifacts` and use a new access-controlled directory outside both repositories.

The checked-in runner is fail-closed: every condition, including baseline, accepts public fixtures only. It rejects company source before loading or executing condition commands, and neither JSON nor a security evidence ID can enable it. After the exact Codebase-Memory native binary passes the dynamic gate and an immutable approved Claude command identity exists, a reviewed future harness release may change that policy. Graphify's company-source rejection must not be weakened.

## Test the Claude Code plugin

```bash
claude plugin validate --strict ./plugins/codegraph-evaluator
claude plugin validate --strict .
claude --plugin-dir ./plugins/codegraph-evaluator
```

The `--plugin-dir` flag also accepts the plugin ZIP generated by Claude Code tooling. This repository's offline bundle uses a local marketplace so the plugin can be installed persistently from an extracted ZIP without GitHub access.

## Build a public offline bundle

```bash
codegraph-harness bundle \
  --version 0.1.0-eval \
  --profile packaging/profiles/public.json \
  --output dist/codegraph-harness-0.1.0-eval.zip
```

Public bundles contain no third-party backend. An internal profile may inject an already approved artifact by relative path and exact SHA-256. The builder rejects traversal, symlinks, duplicate targets, and checksum mismatches.

The candidate registry records discovery inputs only. It currently pins Graphify `v0.9.48` and Codebase-Memory `v0.10.8` to exact commits, but neither project is selected or redistributed.

Static source audit changes the company-source eligibility: pinned upstream Graphify is rejected because its stdio MCP can invoke GitHub-connected PR tools and it contains external LLM paths. Codebase-Memory remains conditional only for an internally verified native binary; its online installers and package wrappers are prohibited, and dynamic zero-egress evidence is still missing. See [Candidate egress audit](docs/candidate-egress-audit.md).

## Backend decision order

1. Upstream artifact, unchanged, with configuration disabled.
2. Upstream artifact behind a thin, stable wrapper.
3. Minimal public fork with an explicit patch ledger.
4. No adoption; keep the baseline workflow.

Move to a lower option only when the higher one fails a documented quality, security, offline-distribution, or operability gate.

## Supported platforms

The source and CI target current GitHub-hosted macOS and Windows runners. This is not a claim that every macOS/Windows version or CPU architecture is supported. The internal acceptance matrix must be based on the actual endpoint inventory.
